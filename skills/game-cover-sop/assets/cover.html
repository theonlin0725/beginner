全局策略

正面约束（4杠杆差异化） + 负面禁止（防玩法误导） = 完整构图策略，这层是全局抽象规则，与「横向 / 竖版」无关。

A. 4 杠杆定义（永久不变 · 跨题材跨容器）

4 杠杆 vs 构图层的关系：构图层(C1-C4)定义单张图的构图参数；4 杠杆(L1-L4)用于多方案差异化比对。
映射：L1 镜头 ≈ C1 视角 ｜ L2 光线 = 全局表现因素·光影 ｜ L3 场景 = 叙事·世界容器 ｜ L4 占比 ≈ C3 面积分配
杠杆它管什么取值池来源构图层映射
L1 镜头视角与拍摄机位（决定观众的"位置"）题材通用：仰角 / 俯视 / 过肩 / 特写 / 远景 / 等距悬浮 …≈ C1 视角
L2 光线戏剧性与情绪（决定观众的"心情"）题材通用：暖光 / 冷暖对撞 / 黄金时刻 / 单光源剧院 …全局·光影
L3 场景世界容器（决定故事在"哪儿"发生）
L3来源说明
L1/L2/L4 是数学层（跨题材通用），L3 是内容层（题材专属）。
L3 取值池 = 那个游戏自己的"世界设定清单"，换游戏 = 清空重来。

以「休闲皇室三消」为例：取值池 = 城堡庭院 / 华丽宴会厅 / 迷宫花园 / 魔法廊柱 / 皇室走廊 / 玻璃花房

方案 A 的 L3 = 宴会厅（暖光，角色在长桌前）
方案 B 的 L3 = 花园（冷暖对撞，角色在喷泉旁）
方案 C 的 L3 = 城堡走廊（顶光，角色在台阶上）
三个方案 L3 完全错开，但都落在同一个取值池里，保持家族感
叙事·世界
L4 占比角色与玩法元素的画面权重（决定"谁是主角"）题材通用：主导 / 平衡 / 玩法主导 / 缺席 / 群像≈ C3 面积

B. 强制差异化规则（数学约束 · 不可妥协）

每两个方案 · 至少错开 3 / 4 个杠杆 否则视为「伪分叉」，必须返工
  • 为什么是 3 不是 2？实证：只错开 2 个杠杆时，人眼扫过去仍觉得"是同一张图换动作"。
  • 为什么是 3 不是 4？4 个全错开会失去 DNA 一致性，跨方案没有家族感。
  • 横向 / 竖版同样适用：这是"做 N 个变体"的差异化数学，与容器比例无关。

C. 负面禁止

📋 填表准则（什么内容该进 C 表？）
入表门槛：实证翻车 — 某个具体「杠杆 × 取值」 → 触发玩法误导 → CTR 高但留存崩 / 被认错品类。仅"不好看"或"美学偏好"不达门槛。
字段格式（4 列）：
  • 杠杆：L1 镜头 / L2 光线 / L3 场景 / L4 占比 / 通用（跨杠杆共振陷阱）
  • 通用高危模式：用一句话描述触发翻车的具体取值（如 "严格正交俯视网格"）
  • 为什么危险：会被误认成哪个品类（如 "暗示桌游 / 棋类"）
  • 缓解方向：怎么改写或破局（如 "改自由角度俯视，去掉网格线"）
✅ 应进入：①新发现的"杠杆 × 取值"翻车组合；②AI 模型新版本带来的新画错倾向；③跨杠杆共振陷阱（同时踩多个 → 暗示某品类）；④从 D 表晋升来的（多个题材都印证的翻车）
❌ 不该进入：单游戏专属翻车（→ 进 D 表）｜取值池正面用法（→ 进 A 表）｜版式禁忌（→ 进 SOP ③ 8 项硬检查 P1-P8）｜审美主观偏好
杠杆通用高危模式为什么危险缓解方向
L1严格正交俯视网格暗示桌游 / 棋类改自由角度俯视，去掉网格线
L1过肩瞄准准星暗示射击 / FPS用第三人称跟随或前景虚化替代
L3明确品类符号场景物：棋盘 / 牌桌 / 球桌 / 转盘 / 老虎机直接被认成对应品类换品类无关的环境，或用悬浮 / 抽象空间替代
L3强写实办公 / 课堂 / 医院暗示模拟经营或剧情解谜非该品类则换抽象 / 奇幻 / 室外背景
L4玩法元素以"精确网格阵列"排布暗示策略 / 桌游改散落 / 漂浮 / 聚合 / 喷发
通用取值显著落入"非本品类品类符号"CTR 高但留存崩Step 8 玩法 Fidelity 自检必须扫一遍
🔄 C ↔ D 晋升路径：D 表是单题材实例翻车（"《Come Match》专属"），C 表是跨题材通用翻车。
晋升触发：当 D 表里某个翻车被 ≥ 2 个不同题材的游戏独立印证后 → 该行从「单题材专属」升级为「跨题材通用」 → 搬运到上方 C 表，并在 D 表保留作"案例溯源"。
这是负面知识的"实证沉淀"机制：先在 D 表里积累具体翻车，等同样的坑被多次踩到，再固化成 C 表的通用禁忌。

D. 项目翻车账本（实证案例库）

每条记录 = 一次具体出图项目里被实证翻车的案例。"翻车风险"不只跟题材有关，还跟目标人群 / 投放渠道 / 市场地区 / subject_type等上下文有关——同一个取值在不同上下文里表现可能完全相反。 本表用 7 列结构记录每条翻车的完整上下文坐标，供后续同条件项目参考、并作为 C 表晋升的数据依据。

📋 字段说明 + 填表准则
7 列字段：
  • 项目 · 批次：游戏名 + 版本 + 出图批次（精确到一次出图）
  • 题材：游戏品类（休闲三消 / 战棋 / 赛车 / RPG / brain teaser / ...）
  • 人群 · 渠道 · 地区：目标用户群 / 投放渠道（FB 买量 / App Store 应用图 / TikTok 短视频...）/ 市场地区（欧美 / 中国 / 中东...）
  • subject_type：character / gameplay_object / hybrid / scenario_puzzle
  • 杠杆 × 取值（命中翻车的具体组合）：例 C1=俯视棋盘 + L4=网格阵列
  • 翻车证据：CTR/留存/调研数据（如 "CTR 8.2% 但 D1 留存 14%（基准 22%），用户调研 70% 误以为是桌游"）
  • 缓解方向 / 是否可晋升 C：怎么改写避免翻车 + 是否已被多个题材独立印证（≥2 → 晋升 C 表）
✅ 应进入：①真实出图后实证翻车（有数据/调研支撑）；②单次案例就值得记录，不必等共性；③上下文越精确越有价值（同一个取值在不同人群/渠道里表现不同时，分两条记）
❌ 不该进入：审美主观偏好（不达"实证翻车"门槛）｜未上线的纯设计阶段问题（→ 走 SOP ③ 8 项硬检查 P1-P8）｜跨题材已被多次印证的（→ 晋升 C 表）｜单纯的取值池正面用法（→ A 表 / DNA 表）
历史预设警告：旧版 D 表用"题材"做唯一分类轴，预设"什么算高危由本游戏的品类决定"。实战中翻车其实和人群、渠道、地区、subject_type、市场上同期友商占位都强相关——同一个画面在 35+ 女性休闲玩家身上是好的，在 25+ 男性硬核玩家身上可能直接翻车。新结构把这些维度都拉出来作为字段。

构图的方法

一张图内部先拆成两层，互不干涉——构图层只管空间结构，表现层只管视觉风格。

构图层（C1-C4）

  • C1 视角：跨格式通用（仰角/俯视/平视）
  • C2 版式骨架：强 Format Adapter 相关，横向常用中心对称/对角线，竖版常用纵向分割/留白优先
  • C3 面积分配：受画幅约束——同一组比例在横向和竖版里视觉感不同，需要调整阈值
  • C4 视觉动线：受画幅约束——横版从左到右，竖版从上到下，读图路径不同

表现因素层

  • 能体现游戏原生美术风格的色彩 / 字体 / 光影 / 质感
    示例
    游戏原生美术风格 = 从 ICON + 游戏截图分析得出的风格锚点，让所有方案保持同一个游戏的视觉基因，换句话说——让玩家一眼认出"这是《某某游戏》的感觉"，而不是不同方案画出不同游戏。

    具体包括：

    色彩 ：主色调 / 配色比例（从截图提取）
    线条 ：线条粗细 / 风格（卡通/写实/扁平）
    角色 ：角色比例 / 表情风格 / 画法
    UI ：UI 元素质感 / 图标风格
  • 多方案分叉的来源——叙事维度
    示例
    5 个故事维度（结构化变量，不是泛泛而谈）：

    1. 时间点（Moment）
    即将发生（悬念） / 动作爆点（冲击） / 结果已发生（成就感）

    2. 角色任务（Character Goal）
    invite（邀请进入） / solve（解决问题） / face_crisis（面对危机） / victory（取得胜利） / discover（发现探索） / guide（带你进入新世界）

    3. 观众关系（Viewer Relation）
    direct_eye_contact（直视玩家） / look_at_target（角色看向画面目标） / back_to_viewer（角色背对，探索感） / multi_character（群像互动）

    4. 冲突强度（Conflict Level）
    none（治愈休闲） / low safe_excitement（大多数休闲游戏的甜点区） / medium（卡牌/策略/RPG） / high（动作/对抗/硬核）

    5. 结果导向（Reward Signal）
    try_it（我想试试）/ nearly_winning（我快赢了）/ loot_rich（奖励很多）/ world_interesting（世界有趣）/ character_lovely（角色可爱）

    本质：锁定 DNA 后，方案间差异来自叙事维度，不是风格差异。
★

表现因素层（通用）

以下内容是从大量案例里归纳出来的共性模式——每次周期性喂图学习后，会根据"反馈进化规则"（§9.2）持续扩充和修正；四个子模块各自有一张选项池表，应用时从游戏类型 + 叙事目标 + DNA 三维度交叉锁定选项，写 prompt 时用的是 SOP 里那几张表，按上面的三步决策法查表选取。

📐 表现层底线（三格式通用 · 不可逾越）
  • 禁止空色块背景：背景至少包含渐变 / 光效 / 斜切 / 纹理 / 粒子 / 剪影之一作为图形化层。纯色块或单一渐变会让画面廉价。
    👉 Banner 场景尤其严格（横版/竖版有主体保护时也不能省）。
  • 颗粒/质感/胶片噪点至少 1 项：避免 AI 生成的"塑料感"（参考"质感"选项池）
  • 层次至少 3 层：前景 / 中景 / 背景必须有视觉层级，否则画面扁平
★

叙事变量（通用）

从用户目标倒推，所有 5 个维度的选择都围绕这个目的展开。

具体决策顺序
决策核心原则：从用户目标倒推，而不是从变量池正推。第一步问自己：这张图要达成什么转化目的？

Step 1：先定 Reward Signal（第 5 维）—— 最终目标
try_it（我想试试）/ nearly_winning（我快赢了）/ loot_rich（奖励很多）/ world_interesting（世界有趣）/ character_lovely（角色可爱）

Step 2：再定 Moment（第 1 维）—— 制造哪种情绪
before（即将发生，悬念）/ during（动作爆点，冲击）/ after（结果已发生，成就感）

Step 3：次定 Conflict Level（第 4 维）—— 安全边界
none（治愈休闲）/ low safe_excitement（大多数休闲游戏的甜点区）/ medium（卡牌/策略/RPG）/ high（动作/对抗/硬核）
⚠️ 休闲游戏绝对不能选 high，那会让玩家觉得游戏好难好累，直接劝退

Step 4：再定 Character Goal（第 2 维）—— 角色在干嘛
invite / solve / face_crisis / victory / discover / guide
同一动作（如"举盾"）在不同 character_goal 下含义完全不同

Step 5：最后定 Viewer Relation（第 3 维）—— 视线往哪指
direct_eye_contact（直视玩家）/ look_at_target（融入故事）/ back_to_viewer（主动探索）/ multi_character（关系感）

完整例子（休闲皇室三消）：
目标：让玩家觉得"游戏有趣，想试试" → try_it
moment = before（悬念吊胃口）
conflict_level = low（休闲游戏甜点区）
character_goal = invite（角色欢迎进入）
viewer_relation = direct_eye_contact（直视玩家，最像邀请）

本质：5 个维度是链式推导关系，不是独立并选。Reward Signal 锁定最终目标 → Moment 决定故事时间点 → Conflict Level 划定强度上限 → Character Goal 自然跟上 → Viewer Relation 收尾视线设计。

#步骤共性动作横 / 竖 / Banner 差异

竖版 9:16 / 2:3 / 3:4 / 4:5
Banner 3.5:1 / 5.2:1 / 8:1（只裁宽不裁高）

4填写表现层色彩 / 字体 / 光影 / 质感 + 商业信息密度三格式通用

7线性化 Prompt把契约转成自然英文段落，按下面「9 段 prompt 模板」结构组织横版 / 竖版 = 5 段（容器 / 主体 / 表现 / 标题 / 负面）
Banner = 9 段（多 1.5 Composition Lock + 1.6 Safe-Crop）

② 主角分型

写 prompt 前先回答一个问题：这张图谁该占 C 位？4 类主角分型决定该用哪个 archetype 池——硬塞错池子（比如三消游戏硬套 character 模板）会导致"角色站中间无意义"。subject_type ≠ 游戏类型（一个三消可能是 character 也可能是 gameplay_object，看这一张图想突出什么）。

主角四分型

subject_type典型案例主体策略archetype 池
characterRoyal Match / Come Match / 角色卡 RPG角色 60%+，face/body 资产强一致11 个 character archetype
gameplay_objectGrill Skewer Pop（三消）/ 物理消除 / 收集类玩法物件 + 玩法证据 + combo burst；角色可缺席或 ≤25%5 个 gameplay_object archetype
hybridGirl Rescue（救援解谜，角色 + 谜题对象）角色 + 玩法 50/50 共存；标题锁两端都要可见character + gameplay_object 池子合并
scenario_puzzleBrain Trick / Brain Test / hidden object / brain teaser情境线索锁：场景里"埋"线索物，等玩家发现3 个 scenario_puzzle archetype

自动判定启发式

  • gameName 正则：含 brain / trick / iq / test / riddle → scenario_puzzle
  • 含 rescue / save / pull / draw → hybrid（角色 + 谜题）
  • 含 match / pop / merge / blast / crush → gameplay_object（三消/合并）
  • 资产证据：character 资产 ≥ 1 张 → character；character = 0 + screenshot 显示物件矩阵 → gameplay_object
  • fallback：无法判定时默认 character（最大兼容性）

③ 9 段 prompt 输出模板 · 跨格式

这 9 段是最终 prompt 的输出结构（① 10 步流程 Step 7 线性化时使用）。横版 / 竖版用其中 5 段（容器 → Title Lock → 主体 → 连接 → 负面），Banner 因贴边裁切风险大额外加段 1.5 Composition Lock 与段 1.6 Safe-Crop。

📋 段落结构 + 扩充准则（这 9 段从哪儿来 / 怎么加新段）
来源：9 段是从大量翻车实证里反向倒推的最小必备结构——每一段都解决一类反复出现的具体翻车（比如段 1 不写 → 模型按默认尺寸出；段 6 不写 → UI/按钮/no text 等高频翻车没拦住）。这不是"设计完美"的产物，是经验沉淀的快照。
段落 DNA（5 字段元组）：每个段都该有这 5 个字段。新增段落时缺一个都不该入表。
  • 段号：整数号（通用段）/ 小数号（格式特化段，如 1.5 仅 Banner）
  • 名称：能在 prompt 里直接当 section header 用（如 [Title Lock]）
  • 职责：这段解决什么问题（一句话）
  • 内容：prompt 里要写的具体英文文案 / 或槽位变量（用 <...> 标）
  • 三格式差异：横/竖/Banner 在这一段的表现差异（值不同 / 取值池不同 / 跳过此段）
  • （隐含）翻车证据：哪次实战的什么翻车导致这段被加进来——不写在表格里但应在 D 表「项目翻车账本」溯源
✅ 应新增段落
  • 新型翻车反复出现，现有 8 段都救不了（如：发现"三消画出来 UI 像截图"，需要"风格基调锁"段说服模型 commercial poster style）
  • 某格式独有的硬约束没地方放（如：竖版海报特有的"商业信息密度锁"——号召力区 / 价格区 / CTA 区留白）→ 用小数号插入
  • AI 模型新版本需要新的引导段（如：新模型默认带水印 → 增加"防水印锁"段）
  • subject_type 扩展导致需要新主体段（如：新增第 5 类 subject_type，段 3 拆成段 3.1/3.2）
❌ 不该新增段落
  • 取值池更新（如新增"暖光"色彩选项）→ 进全局表现因素层
  • 一次性某游戏的特殊文案 → 进 D 表项目翻车账本，不进通用模板
  • 改进 prompt 描述的措辞优化 → 更新对应段「内容」字段，不新增段
  • 纯形式问题（如 negative 漏写、L1-L4 没显式列出）→ 进 ④ 8 项硬检查 P 表，不进段落
  • 纯设计原则（如背景空了、版式散）→ 进 表现层底线 / Banner 构图三条底线，不进段落
编号规则
  • 整数号（段 7 / 段 8）：三格式都需要的通用段
  • 小数号（段 4.5）：仅某格式需要的特化段，标注「仅 X」
  • 差异变体不拆段：如果只是某段在某格式下取值不同（不是缺该职责），写在「三格式差异」列里，不拆新段
扩充工作流：实证翻车 → 判断原因（缺段 / 内容描述不到位 / 仅形式 / 仅设计原则） → 仅当"缺职责段"才新增段落，按 5 字段填齐 → 同时在 D 表登记本次翻车作为段落新增的来源溯源。

④ 标准开场框 + 8 项硬检查（线性化 Prompt 前必过）

📋 标准开场框（每次必输出）
游戏：<游戏名>
玩法识别：<三消 / 解谜 / 救援 / brain teaser / ...>
subject_type：<character / gameplay_object / hybrid / scenario_puzzle>
默认输出：A / B / C 三套独立剧本（每套 4 杠杆错开 ≥3）
横版安全裁切：16:9 母版主体锁中央 75% 宽度，左右各 12.5% 只放可裁切背景，兼容 5:3 / 4:3 / 3:2；2:1 作为横向宽屏特例从 16:9 裁上下
竖版安全裁切：9:16 母版主体锁中央 70% 高度，上下各 15% 只放可裁切背景，兼容 2:3 / 3:4 / 4:5
长条 banner 安全裁切：只裁宽度，不裁高度；标准长条 3.5:1 母版（74%×90% 安全区），超长 5.2:1 母版（76%×90% 安全区），极窄广告条 8:1 母版（74%×90% 安全区）
Banner 构图模板：先选模板再写 prompt（详见 Banner Tab → 03 选择构图模板）
游戏名标题规则：所有 prompt 显式标 `[Title Lock — Flexible Single Title 2.1]`；只保留一层清晰标题，位置可居中/中上/侧中/边缘，但禁止机械贴边和角落小贴片
Negative：禁止裸写 no text；改写 `No extra readable text except the exact game title "<游戏名>"`，并禁止 duplicate title layers / giant background title text

8 项硬检查表（纯 prompt 形式校验 · 三格式通用）

本表只校验 prompt 文本是否合规（标题段格式 / Negative 写法 / 是否多方案 / 杠杆是否显式 ...），不管「画面好不好看」。Banner / 竖版 / 横版的设计原则（版式骨架、面积分配、动线、背景质感）属于构图层 / 表现因素层，请去对应的 Format Adapter 02 构图层 / 全局表现因素层查阅。

#检查项未通过表现修法
P1游戏名是否是单层清晰标题（Title Lock 2.1 段）标题像贴边 logo / UI 标题，只悬浮在顶部或角落；或错误生成双层/背景巨字标题新增独立段 [Title Lock — Flexible Single Title 2.1]：只保留一层清晰标题，位置可居中/中上/侧中/边缘，但禁止机械贴边和角落小贴片。
Banner 子规则：标题必须是主视觉块（宽 25~55% 或 高 40~80%），不是角落 logo
P2Negative 是否裸写 no text / no logo与 P1 自相矛盾，或允许了重复标题层/背景巨字层改 No extra readable text except the exact game title "<游戏名>"，并禁止 duplicate title layers / giant background title text
P3是否默认 A/B/C 三套剧本只给一条 prompt，用户得追问不等用户提醒，默认输出 ≥3 套差异化方案
P4subject_type 是否显式判定所有游戏都按 character archetype 套，无人物题材出"人物广告"开场框先判 subject_type，再选取值池（详见 ② 主角分型）
P5每条 prompt 是否显式写 L1/L2/L3/L4四杠杆藏在 DNA 描述里不可见每条 prompt 都要列 L1 camera: ... · L2 lighting: ... · L3 setting: ... · L4 visual weight: ...
P6差异化矩阵是否先输出方案之间只错 1-2 个杠杆，是伪分叉写 prompt 前先列 4×3 差异化表格，自检至少错 3 行
P7玩法 Fidelity 是否扫高危值休闲拼图画成桌游 / brain teaser 画成动作Step 0.5 玩法 Fidelity 自检，命中高危必须中和或换写法
P8出海素材 safe-crop 是否写入横版/竖版/长条 banner 贴边构图，裁切后标题、主体或玩法证据被切掉；或 banner 错误裁高度导致画面被压扁横版：16:9 中央 75% 宽度；竖版：9:16 中央 70% 高度；banner：只裁宽度三档母版 3.5:1 / 5.2:1 / 8:1，上下不裁高度
⚡

输出前自检 · AI 默认行为规则

线性化 Prompt 后、发送给模型前的最后一道关。这 5 条是默认行为，不需用户提醒。违反任何一条 → 视为 SOP 不合规，需返工。

规则 1：默认出多题材方案 ≥3 个故事题材方案供选择，不需用户提醒
  • 用户没说"只要 1 个" → 默认出至少 3 个方案
  • 每个方案绑定独立的故事维度组合 + 独立的 4 杠杆取值
  • 先输出差异化矩阵，用户确认后再写 prompt
规则 2：每条 prompt 必须显式包含 L1/L2/L3/L4 思考契约 → 线性化时全部写入 prompt，不能省略
  • 每条 prompt 必须显式写出：L1 camera: <值> / L2 lighting: <值> / L3 setting: <值> / L4 visual weight: <值>
  • 示例：L1 camera: low-angle heroic shot · L2 lighting: warm golden hour · L3 setting: throne hall · L4 visual weight: hero dominant 65%+
  • 这四个杠杆必须在 prompt 里可见，不能隐藏在 DNA 描述里不单独写出
规则 3：绝对禁止出现游戏按钮 默认情况下永远不允许，每条 prompt 负面锁必带
  • 默认禁止：购买按钮 / download button / app store badge / 评分按钮 / 分享按钮
  • 每条 prompt 必须包含负面锁：Do not include any purchase button, download button, app store badge, rating button, share button, or any call-to-action button in the image.
  • 例外：只有用户明确要求「强转化买量广告卡」并明确说要展示按钮时才允许
规则 4：主动应用 4 杠杆差异化 不等待用户提醒，这是不需要说的默认行为
  • 每次出多方案时，必须先输出 L1 × L2 × L3 × L4 × N 方案的差异化矩阵表格
  • 自检：每两个方案之间至少错开 3 / 4 个杠杆，否则视为伪分叉需返工
  • 4 杠杆差异化是每次生成多方案时的默认行为，不需要用户说"记得用差异化策略"
规则 5：角色资产剥离（v4.7 升级 — AI 内部闭环） ⚠️ 三次反馈打脸：工具链整合是 AI 本职工作，不是用户负担
  • v4.5 教训：仅在 prompt 写 Subject Lock 段 → 模型不"看"参考图 → 角色被自由重绘
  • v4.6 教训：给用户三条工具路径让他自己选/上传/切平台 → 等于改用户流程、新增工序
  • v4.7 修正：AI 自动跑 3000 MCP 工具链闭环，用户输入端零变化（依然只给 icon + 截图 + 游戏名）
  • 　 ① 3000_comfyui_divide：拆主角 / 配角 / 背景 → 透明 PNG 图层
  • 　 ② 3000_generate_image（model=gpt-image-2, image=PNGs, input_fidelity=high）→ 图生图
  • 　 ③ AI 自己跑异步轮询 + 取图 + 给用户最终图（用户对工具链零感知）
  • 架构教训：v4.6 在工具层立约束没错，错在搞错执行主体——是 AI 调工具，不是让用户调工具
违反处理：未出多方案 / prompt 缺 L1-L4 显式表述 / 无按钮负面锁 / 未先输出差异化矩阵 / 用 generic chibi 自由重绘人物 / 只交付纯 prompt / AI 让用户切平台 or 当工具搬运工 or 自己上传图 → 视为 SOP 不合规，用户可要求返工。AI 必须主动记住这 5 条，不需要用户每次提醒。
